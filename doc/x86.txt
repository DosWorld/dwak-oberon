        Oberon-07/16 programming language compiler for i486
                Windows/Linux/KolibriOS.
------------------------------------------------------------------------------

        Command-line options

  Input - text files of modules with the extension ".mod", encoding ANSI or
UTF-8 with a BOM signature.
  Output - an executable file of PE32, ELF or MENUET01/MSCOFF format.
  Parameters:
  1) name of the main module
  2) application type
      "win32con" - Windows console
      "win32gui" - Windows GUI
      "win32dll" - Windows DLL
      "linux32exe" - Linux ELF-EXEC
      "linux32so"  - Linux ELF-SO
      "kosexe" - KolibriOS
      "kosdll" - KolibriOS DLL

  3) optional options
      -out <file_name> name of the resulting file; by default it
          matches the name of the main module, but with a different
          extension (corresponding to the executable file type)
      -stk <size> stack size in megabytes (2 MB by default,
          values from 1 to 32 MB are allowed)
      -tab <width> tab size (used to calculate coordinates in the
          source text), 4 by default
      -nochk <"ptibcwra"> disable runtime checks (see below)
      -lower allow keywords and predefined identifiers in
          lower case (default)
      -upper upper case only for keywords and predefined
          identifiers
      -def <name> define a conditional compilation symbol
      -ver <major.minor> program version (kosdll only)
      -uses print the list of imported modules
      -fa <size> alignment of PE32 file sections in bytes, possible values:
          512, 1024, 2048, 4096. 512 by default

      the -nochk option is given as a string of characters:
      "p" - pointers
      "t" - types
      "i" - indexes
      "b" - implicit conversion of INTEGER to BYTE
      "c" - range of the argument of the CHR function
      "w" - range of the argument of the WCHR function
      "r" - equivalent to "bcw"
      "a" - all checks

      The order of the characters may be arbitrary. The presence of a
      particular character in the string disables the corresponding check.

      For example: -nochk it - disable index checking and type guarding.
      -nochk a - disable all checks that can be disabled.

  For example:

  Compiler.exe "C:\example.mod" win32con -out "C:\example.exe" -stk 1
  Compiler.exe "C:\example.mod" win32dll -out "C:\example.dll"
  Compiler.exe "C:\example.mod" win32gui -out "C:\example.exe" -stk 4
  Compiler.exe "C:\example.mod" win32con -out "C:\example.exe" -nochk pti
  Compiler.kex "/tmp0/1/example.mod" kosexe -out "/tmp0/1/example.kex" -stk 4
  Compiler.kex "/tmp0/1/example.mod" kosdll -out "/tmp0/1/mydll.obj" -ver 2.7
  Compiler.exe "C:\example.mod" linux32exe -out "C:\example" -stk 1 -nochk a

  If compilation succeeds, the compiler returns exit code 0, otherwise 1.
When the compiler runs under KolibriOS, no exit code is returned.

------------------------------------------------------------------------------
        Differences from the original

1.      The pseudo-module SYSTEM has been extended
2.      The character "_" is allowed in identifiers
3.      System flags have been added
4.      The CASE statement has been improved (constant expressions in case
        labels and an optional ELSE branch have been added)
5.      The set of standard procedures has been extended
6.      The semantics of type guarding/testing has been refined for the null
        pointer
7.      One-line comments have been added (they start with the pair of
        characters "//")
8.      Inheritance from a pointer type is allowed
9.      Syntax has been added for importing procedures from external libraries
10.     "Strings" may also be enclosed in single quotes: 'string'
11.     The type WCHAR has been added
12.     The operation of concatenating string and character constants has been
        added
13.     Modules may be imported with a path and a file name
14.     Special syntax has been added for conditional compilation (see CC.txt)
15.     The procedure name at the end of the declaration (after END) is
        optional
16.     Lower case is allowed for keywords

------------------------------------------------------------------------------
        Implementation notes

1.      Basic types

          Type             Range of values                 Size, bytes

        INTEGER       -2147483648 .. 2147483647                 4
        REAL          4.94E-324 .. 1.70E+308                    8
        CHAR          ASCII character (0X .. 0FFX)              1
        BOOLEAN       FALSE, TRUE                               1
        SET           set of integers {0 .. 31}                 4
        BYTE          0 .. 255                                  1
        WCHAR         Unicode character (0X .. 0FFFFX)          2

2.      Maximum length of identifiers - 255 characters
3.      Maximum length of string constants - 511 characters (UTF-8)
4.      Maximum number of dimensions of open arrays - 5
5.      The procedure NEW fills the allocated memory block with zeros
6.      Global and local variables are initialized to zeros
7.      Unlike many Oberon implementations, there is no garbage collector and
        no dynamic module loading
8.      In expressions, the type BYTE is always converted to INTEGER
9.      Overflow of expression values is not checked
10.     Runtime errors:

 1      ASSERT(x), if x = FALSE
 2      dereference of the null pointer
 3      integer division by a non-positive number
 4      call of a procedure through a procedure variable with a null value
 5      type guard error
 6      array bounds violation
 7      unhandled expression value in a CASE statement
 8      array copy error v := x, if LEN(v) < LEN(x)
 9      CHR(x), if (x < 0) OR (x > 255)
10      WCHR(x), if (x < 0) OR (x > 65535)
11      implicit conversion of x:INTEGER to v:BYTE, if (x < 0) OR (x > 255)

------------------------------------------------------------------------------
        The pseudo-module SYSTEM

  The pseudo-module SYSTEM contains low-level and unsafe procedures; errors
made when using procedures of the pseudo-module SYSTEM may lead to corruption
of runtime data and abnormal termination of the program.

        PROCEDURE ADR(v: any type): INTEGER
                v - a variable or a procedure;
                returns the address of v

        PROCEDURE SADR(x: string constant (CHAR UTF-8)): INTEGER
                returns the address of x

        PROCEDURE WSADR(x: string constant (WCHAR)): INTEGER
                returns the address of x

        PROCEDURE VAL(T; v: any type): T
                v - a variable;
                interprets v as a variable of type T

        PROCEDURE SIZE(T): INTEGER
                returns the size of type T

        PROCEDURE TYPEID(T): INTEGER
                T - a record type or a pointer type,
                returns the type number in the table of record types

        PROCEDURE INF(): REAL
                returns the special real value "infinity"

        PROCEDURE MOVE(Source, Dest, n: INTEGER)
                Copies n bytes of memory from Source to Dest,
                the areas Source and Dest must not overlap

        PROCEDURE GET(a: INTEGER;
                VAR v: any basic type, PROCEDURE, POINTER)
                v := Memory[a]

        PROCEDURE GET8(a: INTEGER;
                       VAR x: INTEGER, SET, BYTE, CHAR, WCHAR, SYSTEM.CARD32)
                Equivalent to
                SYSTEM.MOVE(a, SYSTEM.ADR(x), 1)

        PROCEDURE GET16(a: INTEGER;
                        VAR x: INTEGER, SET, WCHAR, SYSTEM.CARD32)
                Equivalent to
                SYSTEM.MOVE(a, SYSTEM.ADR(x), 2)

        PROCEDURE GET32(a: INTEGER; VAR x: INTEGER, SET, SYSTEM.CARD32)
                Equivalent to
                SYSTEM.MOVE(a, SYSTEM.ADR(x), 4)

        PROCEDURE PUT(a: INTEGER; x: any basic type, PROCEDURE, POINTER)
                Memory[a] := x;
                If x: BYTE or x: WCHAR, the value of x is extended
                to 32 bits; use SYSTEM.PUT8 to write bytes,
                and SYSTEM.PUT16 for WCHAR

        PROCEDURE PUT8(a: INTEGER;
                       x: INTEGER, SET, BYTE, CHAR, WCHAR, SYSTEM.CARD32)
                Memory[a] := the low 8 bits of (x)

        PROCEDURE PUT16(a: INTEGER;
                        x: INTEGER, SET, BYTE, CHAR, WCHAR, SYSTEM.CARD32)
                Memory[a] := the low 16 bits of (x)

        PROCEDURE PUT32(a: INTEGER;
                        x: INTEGER, SET, BYTE, CHAR, WCHAR, SYSTEM.CARD32)
                Memory[a] := the low 32 bits of (x)

        PROCEDURE COPY(VAR Source: any type; VAR Dest: any type; n: INTEGER)
                Copies n bytes of memory from Source to Dest.
                Equivalent to
                SYSTEM.MOVE(SYSTEM.ADR(Source), SYSTEM.ADR(Dest), n)

        PROCEDURE CODE(byte1, byte2,... : INTEGER)
                Insertion of machine code,
                byte1, byte2 ... - constants in the range 0..255,
                for example:
                SYSTEM.CODE(08BH, 045H, 008H) (* mov eax, dword [ebp + 08h] *)

  The module SYSTEM also defines the type CARD32 (4 bytes). No explicit
operations are allowed for the type CARD32, except for assignment.

  The functions of the pseudo-module SYSTEM cannot be used in constant
expressions.

------------------------------------------------------------------------------
        System flags

  When declaring procedure types and global procedures, a calling convention
flag may be specified after the keyword PROCEDURE: [stdcall], [cdecl],
[fastcall], [ccall], [windows], [linux], [oberon]. For example:

        PROCEDURE [ccall] MyProc (x, y, z: INTEGER): INTEGER;

  If the flag [ccall] is specified, the cdecl convention is adopted, but
before the call the stack pointer is aligned to a 16-byte boundary.
  The flag [windows] is a synonym for [stdcall], [linux] is a synonym for
[ccall]. A "-" after the flag name ([stdcall-], [linux-], ...) means that the
result of the procedure may be ignored (not allowed for the type REAL).
  If no flag is specified, or the flag [oberon] is specified, the internal
calling convention is adopted.

  When declaring record types, the flag [noalign] may be specified after the
keyword RECORD. The flag [noalign] means that the fields of the record are not
aligned. Records with a system flag cannot have a base type and cannot be base
types for other records.
  To use system flags, SYSTEM must be imported.

------------------------------------------------------------------------------
        The CASE statement

  Syntax of the CASE statement:

        CaseStatement =
                CASE Expression OF Case {"|" Case}
                        [ELSE StatementSequence] END.
        Case = [CaseLabelList ":" StatementSequence].
        CaseLabelList = CaseLabels {"," CaseLabels}.
        CaseLabels = ConstExpression [".." ConstExpression].

  For example:

        CASE x OF
        |-1:    DoSomething1
        | 1:    DoSomething2
        | 0:    DoSomething3
        ELSE
                DoSomething4
        END

  Constant expressions may be used in case labels, and the ELSE branch is
optional. If the value of x matches none of the variants and there is no ELSE,
the program is terminated with a runtime error.

------------------------------------------------------------------------------
        The WCHAR type

  The type WCHAR has been added to the language for convenient Unicode support.
For the types WCHAR and ARRAY OF WCHAR, all the same operations are allowed as
for the types CHAR and ARRAY OF CHAR, with the exception of the predefined
procedure CHR, which returns only the type CHAR. To obtain a value of type
WCHAR, the procedure WCHR should be used instead of CHR. For correct handling
of the type, the source text must be saved in UTF-8 encoding with BOM.

------------------------------------------------------------------------------
        Concatenation of string and character constants

  Concatenation ("+") of constant strings and characters of type CHAR is
allowed:

  str = CHR(39) + "string" + CHR(39); (* str = "'string'" *)

  newline = 0DX + 0AX;

------------------------------------------------------------------------------
        Type test and type guard for the null pointer

  The original language report does not define the behavior of a program when
the type guard p(T) and the type test p IS T are performed with p = NIL. In
many Oberon implementations, performing such an operation leads to a runtime
error. In this implementation, a type guard of the null pointer does not lead
to an error, and the type test yields FALSE. In a number of cases this makes it
possible to reduce the use of type guards considerably.

------------------------------------------------------------------------------
        Additional standard procedures

        DISPOSE (VAR v: any pointer)
                Frees the memory allocated by the procedure NEW for the
                dynamic variable v^, and assigns the value NIL to the
                variable v.

        COPY (x: ARRAY OF CHAR/WCHAR; VAR v: ARRAY OF CHAR/WCHAR);
                v := x;
                If LEN(v) < LEN(x), the string x is copied
                incompletely

        LSR (x, n: INTEGER): INTEGER
                Logical shift of x to the right by n bits.

        MIN (a, b: INTEGER): INTEGER
                Minimum of two values.

        MAX (a, b: INTEGER): INTEGER
                Maximum of two values.

        BITS (x: INTEGER): SET
                Interprets x as a value of type SET.
                Performed at compile time.

        LENGTH (s: ARRAY OF CHAR/WCHAR): INTEGER
                Length of the 0X-terminated string s, not counting the
                character 0X. If the character 0X is absent, the function
                returns the length of the array s. s cannot be a constant.

        WCHR (n: INTEGER): WCHAR
                Type conversion, similar to CHR(n: INTEGER): CHAR

------------------------------------------------------------------------------
        Importing modules with a path and a file name

Examples:

    IMPORT Math IN "./lib/math.mod"; (* relative to the current module *)

    IMPORT M1 IN "C:\lib\math.mod"; (* absolute path *)

------------------------------------------------------------------------------
        Imported procedures

  Import syntax:

  PROCEDURE [callconv, library, function] proc_name (FormalParam): Type;

  - callconv -- calling convention
  - library -- name of the dynamic library file (string constant)
  - function -- name of the imported procedure (string constant); if an empty
  string is specified, the procedure name = proc_name

  for example:

  PROCEDURE [windows, "kernel32.dll", ""] ExitProcess (code: INTEGER);

  PROCEDURE [stdcall, "Console.obj", "con_exit"] exit (bCloseWindow: BOOLEAN);

  An (optional) "END proc_name;" may be added at the end of the declaration

  Declarations of imported procedures must be located in the global scope of
  the module after the variable declarations, together with the declarations
  of "ordinary" procedures, from which imported ones differ only by the absence
  of a procedure body. Otherwise the same rules apply to such procedures:
  they can be called, assigned to a procedure variable, or their address can be
  obtained.

  Since an imported procedure always has an explicit calling convention, a
  compatible procedure type must also be declared with an explicit calling
  convention:

  VAR
      ExitProcess: PROCEDURE [windows] (code: INTEGER);
      con_exit:    PROCEDURE [stdcall] (bCloseWindow: BOOLEAN);

  In KolibriOS, procedures can be imported only from libraries located
  in /sys/lib. It is not necessary to import and call the library
  initialization functions (lib_init, START).

  For Linux, imported procedures are not implemented.

------------------------------------------------------------------------------
        Hidden procedure parameters

  Some procedures may have hidden parameters; they are absent from the list of
formal parameters, but are taken into account by the compiler when translating
calls. This is possible in the following cases:

1.      The procedure has a formal parameter that is an open array:
                PROCEDURE Proc (x: ARRAY OF ARRAY OF REAL);
        The call is translated as:
                Proc(LEN(x), LEN(x[0]), SYSTEM.ADR(x))
2.      The procedure has a formal variable parameter of type RECORD:
                PROCEDURE Proc (VAR x: Rec);
        The call is translated as:
                Proc(SYSTEM.TYPEID(Rec), SYSTEM.ADR(x))

  Hidden parameters must be taken into account when interfacing with external
applications.

------------------------------------------------------------------------------
        The RTL module

  All programs implicitly use the module RTL. The compiler translates some
operations (type test and type guard, string comparison, runtime error messages
and others) as calls to procedures of this module. These procedures should not
be called explicitly.
  Runtime error messages are output in dialog boxes (Windows), to the terminal
(Linux), to the debug board (KolibriOS).

------------------------------------------------------------------------------
        The API module

  There are several implementations of the module API (for different OSes).
  Like the module RTL, the module API is not intended for direct use. It
provides the interface between RTL and the OS.

------------------------------------------------------------------------------
        Generation of DLL executable files

  Only procedures may be exported. For this, the procedure must be located in
the main module of the program, and its name must be marked with the export
symbol ("*"). Procedures that are imported from other dll libraries cannot be
exported.

  KolibriOS DLLs always export the identifiers "version" (program version) and
"lib_init" - the address of the DLL initialization procedure:

        PROCEDURE [stdcall] lib_init (): INTEGER

This procedure must be called before using the DLL.
The procedure always returns 1.
